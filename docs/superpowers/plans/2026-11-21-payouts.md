# Payouts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a project attach payees' shares to its payments. APICenter holds each share until the project releases it, then pays pooled earnings from the PayMongo wallet: weekly, plus on-demand cash-out, each payout sent exactly once. The feature is exposed through the public API, the SDK, events and the management console, with no PayMongo child accounts.

**Architecture:** The payouts feature lives in the payments runtime (`apps/payments/src/features/payouts/`). It has eight parts:
- pure ledger and policy modules
- a Postgres store with an in-memory fallback
- a `MoneyMover` port with PayMongo batch-transfer and mock adapters
- an exactly-once executor and reconciler
- a Cloud Run runner job
- payout events, written to the existing payment event outbox
- gateway public operations and console admin routes, both of which forward to the runtime with a signed context
- a console "Payouts" project section

Every record goes through a merchant-account resolver, so a later move to linked accounts is a data change.

**Tech Stack:**
- Runtime: TypeScript on Node 24, Express 5, `pg`, zod and Jest 30.
- Gateway: NestJS.
- Console: Next.js 16 App Router, TanStack Query and Vitest.
- Contracts: OpenAPI 3.2 and AsyncAPI 3.1.
- Data and jobs: Supabase Postgres migrations and Cloud Run jobs.

**Spec:** [docs/superpowers/specs/2026-11-21-payouts-design.md](../specs/2026-11-21-payouts-design.md) and [ADR-0008](../../adr/0008-project-payouts-through-resolved-merchant-accounts.md). Read both before starting.

## Global Constraints

**Money**
- Amounts are integer centavos (`Number.isSafeInteger`), and the currency is always `'PHP'` (ADR-0004).
- A payee is a generic recipient. Docs and code never name a consumer product.

**Scoping**
- Every payout row carries `environment`, `owner_tribe_id`, `project_id`, `consumer_service_id` (the application that created the payee or allocation) and `merchant_account_id`. Rows of one project are never visible to another.
- Runtime scoping uses `PaymentContext.projectId`: the signed `own_prj`, so migrated projects keep their legacy owner.

**PayMongo**
- The source BIC is `PAEYPHM2XXX`. The GCash BIC is `GXCHPHM2XXX`. Receiving institutions come from `GET /v1/wallets/receiving_institutions?provider=instapay`.
- Each transfer is sent as a batch of one: `POST /v2/batch_transfers` with `{ transfers: [item] }`.
  - `provider` is `instapay` for an `instapay` destination and `paymongo` for a `paymongo_wallet` destination.
  - InstaPay is capped at 5,000,000 centavos per transfer. A larger pool pays across runs.
- The default fee is 1000 centavos per transfer. The actual fee comes from PayMongo's response.

**Policy**
- The default policy is a weekly payout on Friday at 20:00 Asia/Manila, plus on-demand cash-out with a minimum of 10_000 and a daily cap of 1_000_000.
- The platform bears the fee on scheduled payouts, and the payee bears it on cash-outs.
- After a destination change, payouts to that payee are held for 24 hours.

**Safety**
- A payout whose submission outcome is unknown is never resubmitted. Only the reconciler or an operator resolves it.
- A runtime in `live` mode refuses to submit unless `PAYOUTS_LIVE_ENABLED=true`, with code `PAYOUTS_LIVE_DISABLED`.

**Conventions**
- Migrations are single `BEGIN … COMMIT` files in `supabase/migrations/`. Each enables RLS, grants `SELECT, INSERT, UPDATE` to `payments_runtime`, and adds a `payments_runtime` policy, following `20261113000500_payment_replay_attempts.sql`.
- Public operations: every payments mutation declares `IdempotencyKey` and a `409` response with `IdempotencyConflict`. No `paymongo_` appears anywhere in the public contracts. Public events use `contractVersion: '2.0'`.
- Releases: SDK 3.3.0 and contracts 1.2.0. These versions and the migration are recorded in the root `CHANGELOG.md` under Unreleased → Added.

## Review Focus

These are the failure modes most likely to hurt a user, most likely first. Each names the task that pins it.

1. **Paying twice after a timeout or crash.** An `unknown` payout is never resubmitted, and two concurrent runs create one payout. Pinned in Task 6: `never resubmits an unknown payout` and `two concurrent runs create one payout`.
2. **A refund after money left.** A refund on a `pooled` or `paid` allocation creates a negative adjustment that the next payout nets, and a non-positive pool pays nothing. Pinned in Task 1 (`refundEffect`, `composePayout` with `not_positive`) and Task 7 (`refund after payout claws back on next payout`).
3. **Cross-project payees.** Allocations naming another project's payee are rejected with 404 and store nothing, and the console admin routes enforce project access too. Pinned in Task 7 (`rejects allocations for another project's payee`) and Task 13 (`refuses a project the actor cannot read`).
4. **Missed or doubled weekly runs.** An hourly runner pays a pool once per weekly slot, and catches up after a missed run. Pinned in Task 2 (`latestScheduledSlot` and the `lastScheduledPayoutAt` cases) and Task 6 (`a second schedule run in the same week pays nothing`).
5. **Low float and a fresh destination.** A payout that would overdraw the wallet stays unpooled, and the report says `float_low`. A destination changed less than 24 hours ago is not paid. Pinned in Task 6 (`skips payees when the float is too low and reports float_low`) and Task 8 (`destination change holds payouts for 24h`).
