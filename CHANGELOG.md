# Changelog

User-visible changes are recorded under Unreleased until a release is cut. This file starts with the documentation governance update; it does not reconstruct previous releases.

## Unreleased

### Breaking

- Payment errors are provider-neutral: a provider rejection returns `PAYMENT_REQUEST_INVALID` (400), `PAYMENT_DECLINED` (402, with `details.reason`), `NOT_FOUND`, `PROVIDER_RATE_LIMITED` (429), `PROVIDER_UNAVAILABLE` (503) or `PROVIDER_ERROR` (502), with APICenter's own message. Provider error codes, messages and response bodies are no longer returned. Until 2027-03-01 the provider's code is also returned as the deprecated `details.deprecatedProviderCode`, with `Deprecation` and `Sunset` headers. A failed intent's `lastPaymentError.code` is now a neutral reason (`insufficient_funds`, `card_expired`, `invalid_card_details`, `card_declined`, `authentication_failed`, `cancelled_by_payer`, `processor_unavailable`, `other`), with the provider's code in the deprecated `lastPaymentError.deprecatedProviderCode` until the same date. A payout's `failureCode` is one of `insufficient_funds`, `invalid_destination`, `rate_limited`, `wallet_not_configured`, `rejected`, `failed` or `not_submitted` (ADR-0010).
- Test keys deliver email, SMS and OTP only to the project's registered test recipients (Management → **Settings** → **Test recipients**). A test send to anyone else succeeds and is recorded but is not delivered, and the response carries `X-APICenter-Test-Delivery: suppressed`; a suppressed OTP returns its `code` so automated tests can verify it. Live is unchanged.
- SMS: without a pinned sender, a request's `senderId` must be APICenter's default sender; any other value returns `403 SENDER_NOT_APPROVED`. Messages go out on APICenter's provider account, so a free-form sender ID let a project send as any brand. Ask an operator to pin your sender ID.
- SDK 3.0.0, for application keys only. `new ApiCenter()` reads `APICENTER_API_KEY`; `baseUrl`, `APICENTER_URL`, service credentials, access-token providers, `paymentApiKey` and `setup.status()` are removed. Writes generate an idempotency key when none is given and retry network errors, timeouts, 408, 429 and 5xx with the same key, respecting `Retry-After`. Failures are typed (`AuthenticationError`, `PermissionError`, `ValidationError`, `NotFoundError`, `IdempotencyError`, `RateLimitError`, `QuotaExceededError`, `ServerError`, `ConnectionError`) and carry `requestId`. Methods are renamed for consistency (`email.get`, `sms.get`, `otp.send`, `otp.get`, `geo.geocode`, `geo.checkGeofence`, `auth.google.*`). New: `whoami()`, `payments.records.listAll()`, `isPending()`, request hooks, per-call timeouts, `createWebhookHandler()`, and typed webhook events. Webhook and published-API verification use WebCrypto (now async), so the SDK runs on Node 20+, Deno, Bun and edge runtimes. Ships ES modules and CommonJS. See `packages/sdk/UPGRADING.md`.
- Payment event contract 2.0 and contracts 1.0.0: events carry `environment`, `organizationId`, `projectId` and `applicationId`; `ownerTribeId`, `ownerGroupId`, `consumerServiceId` and the duplicated `data` fields are gone, and a paid checkout's `data` is `{ status, checkoutId, paymentId, amount, currency }` with `amount` in minor units. The AsyncAPI contract now lists only the event that is published (`payment.checkout.paid`) and describes signed webhook delivery.
- Removed the sandbox tribe examples, the AlphaCI payment smoke harness, and the consumer guides for service registration, token exchange, registry health and Pub/Sub push delivery.
- Removed the legacy access model. The gateway no longer has tribes, the service registry and service registration, service tokens and refresh tokens (`/api/v1/auth/*`), service secrets and their rotation, payment API keys, the tribe-to-tribe and external proxies (`/api/v1/tribes/*`, `/api/v1/external/*`), tribe quotas, plans and the tribe rate limiter, the catalog, developer portal, policy, entitlement, promotion, change-request and analytics features, the generic approvals API, compliance export, verification runs, and the Vault, Descope, Kafka and internal-JWT settings. Every consumer call needs an application key (`ak_test_…`/`ak_live_…`); `/api/v1/shared/*` and `/api/v1/payments/*` answer 401 without one. The admin API is the control plane's (`/api/v1/admin/control-plane/*`) plus payment event provisioning and request diagnostics, behind the platform credential only.
- Runtimes accept only the gateway's signed runtime context in production; the legacy `X-Tribe-Id`/`X-APICenter-Source-Service-Id` headers are ignored, and outside production a call without a context is a fixed local caller. Runtimes no longer register themselves with the gateway (`REGISTER_WITH_GATEWAY` is gone).
- The console keeps Projects, People, Requests and Settings; the tribe registry, catalog, quotas, plans, dashboards, data pipeline, Confluent, readiness, smoke-test and migration pages are removed. Sign-in looks up memberships at `GET /api/v1/admin/control-plane/memberships`.
- The public OpenAPI has one security scheme, `ApplicationKey`, drops `/api/v1/auth/*`, and adds `/api/v1/whoami`. Reference snippets use `APICENTER_API_KEY`.
- Removed the release verifier and its workflow, the post-deploy and tribe smoke scripts, the legacy-routing guard, and the local Vault container.

### Added

- SDK 3.5.0 and contracts 1.4.0 add test payee wallet onboarding, hosted verification links and `payee.onboarding.updated`. The test feature defaults to off and requires migration `20261124001600`.

- Projects can record who verified a payee, when, and how through `PUT /api/v1/payments/payees/{payeeId}/verification` and SDK 3.4.0. The payouts runtime can require that record with `PAYOUTS_REQUIRE_PAYEE_VERIFICATION=true`. Contracts are version 1.3.0.
- The payouts console can preview linked-merchant onboarding in test behind environment and project switches. Collections and payouts retain their merchant account across project moves. Live onboarding is pending PayMongo verification.

- Payouts:
  - **Payees and allocations.** Register payees with `POST /api/v1/payments/payees` and set where they are paid with `PUT /api/v1/payments/payees/{payeeId}/destination`: InstaPay (GCash or bank) or a provider wallet, held for 24 hours after a change. Attach `allocations` to checkouts, payment intents and payment links. Each is held when the payment is paid, then released or cancelled with `POST /api/v1/payments/allocations/{allocationId}/release|cancel`.
  - **When payees are paid.** Released earnings are pooled per payee and paid weekly (Friday 20:00 Asia/Manila by default), or on `POST /api/v1/payments/payees/{payeeId}/cash-out` within a daily cap.
  - **Following payouts.** `GET /api/v1/payments/payouts` lists payouts. A refund after a payout is recovered from the payee's next payout.
  - **Scopes and events.** New scopes `payments:payouts:read` and `payments:payouts:write`. New events `payment.allocation.held`, `payment.payout.paid` and `payment.payout.failed` (AsyncAPI 2.2.0).
  - **SDK and contracts.** SDK 3.3.0 adds `payments.payees`, `payments.allocations`, `payments.payouts` and the new event types. Contracts 1.2.0 adds the payout types.
  - **Deployment.** Requires migration `20261121001200`. Live money movement stays off until `PAYOUTS_LIVE_ENABLED=true`. See `docs/operations/payouts-runbook.md`.

- Lifecycle actions: suspend and resume an application (its keys and workload identities are refused with `APPLICATION_INACTIVE`), archive and restore a project (every request refused with `PROJECT_INACTIVE`, nothing deleted), and delete a team (its project roles go with it, unless it is a project's only administrator). Each is in the console and audited.
- Public guides "Errors and retries" (the error response, which failures to retry, and the common codes) and "Versions and changes" (what v1 may add at any time, and how breaking changes ship).
- SDK 3.2.0: `error.retryable` says whether the same request may succeed if sent again. The SDK's own retries use the same rule.
- The OpenAPI documents 401, 403, 429 (with `Retry-After`), 500, 502 and 503 (with `Retry-After`) on every payments operation.
- SDK 3.1.0 and contracts 1.1.0 carry the payment additions below: wallet intents, checkout `paymentMethods`, app return links and the `payment.intent.paid` / `payment.intent.failed` event types.
- Open GCash or Maya directly: `POST /api/v1/payments/intents` (`payments.intents.create`) with `paymentMethod` (`gcash` or `paymaya`) and `returnUrl` creates the intent, the wallet payment method and the attachment in one call and returns `nextAction.redirectUrl`, which goes straight to the wallet. An optional `billing` carries the customer's name, email and phone.
- Checkouts accept `paymentMethods` to limit the checkout page, for example to `["gcash"]`.
- Payment return links can be the app's own links (`myapp://…`) for checkouts and intents. The gateway hands the provider a signed HTTPS page, `/api/v1/payment-return/<token>`, that forwards to the app link and to nothing else. `javascript:`, `data:` and similar links are rejected.
- Events `payment.intent.paid` and `payment.intent.failed` (AsyncAPI 2.1.0, contract 2.0, `aggregateType: "payment_intent"`), delivered like `payment.checkout.paid` and typed in the SDK. A failed attempt sets the intent's status to `failed` with `lastPaymentError`; a failure that arrives after the intent succeeded is ignored.
- `GET /api/v1/payments/capabilities` lists the methods enabled for the environment (`APICENTER_PAYMENT_METHODS_TEST` / `_LIVE`, default all four). Asking a checkout or intent for any other method returns `400 PAYMENT_METHOD_UNAVAILABLE`.

### Changed

- Console lists of projects, members and an application's keys load in pages of 100 with **Load more** (gateway: `limit`, `cursor` and `meta.nextCursor` on those routes). Pickers and navigation load the first 200. The platform organization list counts projects and members in the database instead of loading every row.
- Hosting: the gateway, the console and the email, SMS, OTP, Google sign-in, geolocation and payments runtimes run in `australia-southeast1`, beside the database, instead of `asia-southeast1`. Console pages that made about a hundred cross-region database round trips now answer in under a second. Docs and webhooks stay in `asia-southeast1`.
- The management console is redesigned: a neutral, dense look with light and dark themes; an organization switcher, ⌘K search, and per-project Test/Live switching with live marked in red. Projects live at `/projects/:projectId/:env` with Overview (status, plan, last-24-hour usage by application and action, going live), Applications (an application page with Access and Keys tabs: grant several actions at once, choose a key's expiry, revoke with a reason) and Capabilities (switches; turning one off or changing live asks first). People shows members with roles and teams. Actions a person's role does not allow are disabled with the reason instead of failing. Requests and Settings are shown to platform operators only. Old `/control-plane/*` links redirect.
- Console: capability settings and webhooks. Capabilities gets a Configure sheet for the email sender (it cannot be read back, so saving replaces it) and Google sign-in (redirect URIs, display name, your own OAuth client with a write-only secret, switch back to the shared client or remove); saving in live asks first. A new Webhooks section per environment lists payment event destinations with their status and provisioning errors, adds a signed HTTPS webhook (the secret is shown once, with verification guidance) or a Pub/Sub push destination, rotates a signing secret with a 24-hour overlap, and disables a destination. Applications get a Webhook tab.
- Console: project settings, quotas and workload identities. `/projects/:projectId/settings` assigns, changes and removes project roles for members and teams (warning before removing the last explicit admin) and suspends or resumes test and live. Quotas per environment (`/projects/:projectId/:env/quotas`) and shared ceilings across projects (`/quotas`, organization owners and admins) can be created, disabled and re-enabled; enforcing one in live asks first, and the page says the gateway cannot edit or delete policies or report usage. Applications get a Workload identities tab to bind and revoke Google service accounts that call APICenter with a Google ID token instead of an API key.
- Console: published APIs. A new APIs section per environment publishes HTTP APIs (name, slug, public https upstream, and operations mapping a method and `{param}` path to an action), checked against the gateway's rules before sending; an API's page edits the upstream and operations (saving replaces them all; live edits ask first) and enables or disables it. Project admins approve or reject incoming access requests (not their own; rejection records no reason). The organization API catalog (`/apis`) lists every active API with its operations. The application Access tab gains API access: see and revoke API grants, and request an action on another API, granted at once in the same project or sent to the owning project's admins.
- Console: the sign-in screen, the Google-not-configured and deployment-blocked screens, and the public landing page use the console design system in light and dark. Sign-in shows distinct errors for no access, a failed access lookup, a missing Google client ID and a Google script failure. The landing page previews the console's application Access page and describes only shipped features. Removed the legacy landing palette and animations, a dead Terms link and about 12 MB of unused landing images; the logo stays legible in dark mode.
- Console: organizations, approvals and invites. Platform operators create (optionally with a first owner), rename, suspend and reactivate organizations at `/organizations`; names may not contain control characters. A suspended organization's applications are refused (`ORGANIZATION_INACTIVE`) and it cannot create projects, but its members can still sign in and change settings. `/approvals` lists pending live activations and API access requests: every organization's for platform operators, and the ones the person can decide for everyone else; each opens the page where it is decided. A new member gets an invite email from the email runtime's new `POST /admin/platform-messages` route; when it cannot be sent the console shows a copyable invite, and the outcome is audited as `control_plane.member.invite_sent` or `invite_not_sent` with a reason code. An invite to the same email and organization is sent at most once in 24 hours.
- Console: observability. Each environment has a request log (`/projects/:projectId/:env/requests`, also on each application) with filters, request details and correlation IDs. The overview shows usage over 24 hours, 7 days or 30 days with daily-limit progress and the project's recent activity; quota pages show how much of each policy is used, warning from 80%. A new audit log (`/audit`) filters by project, actor, action and time for organization owners and admins, and for project admins on their own projects; platform operators can widen it to every organization. Audit events now record their organization and project (migration `20261120001020`).
- Console: developer experience. Each environment overview has a getting-started checklist with a ready-to-copy SDK snippet. Keys that expire within 14 days are flagged on the Keys tab, the overview and the sidebar. Webhooks show their delivery history (status, latency, attempt, error) and can send a `webhook.test` event, on the Webhooks page and the application Webhook tab, at most once every 10 seconds per destination. The webhooks runtime stores the history in `shared_webhooks.webhook_deliveries` for 30 days (migration `20261120001030`).
- Console: capability settings. Email shows its current sender and daily limit. SMS can pin a sender ID; a request that names a different `senderId` is then refused with `403 SENDER_NOT_APPROVED`. OTP can set the code length, expiry, maximum wrong attempts and a one-line message template that must contain `{{code}}` and no links, addresses or phone numbers; only a project admin can change the template. Once the attempts are used up, verify returns `400 OTP_ATTEMPTS_EXCEEDED`. The payments row shows whether the organization has a merchant binding (`GET …/organizations/:id/payments/merchant-binding`) and why payments cannot be enabled without one; geolocation says it has no per-project settings. Requires migration `20261120001040`.
- Console: control-plane gaps. Quota policies can be edited and deleted (a soft delete that cannot be undone); a policy's counter is keyed by its window length (`policy:<id>:<windowSeconds>`), so changing the window starts a new count. Signed webhooks can be limited to chosen payment event types; `webhook.test` is always delivered and Pub/Sub push destinations still receive every type. A project lists the API access requests it has sent, with the reason when one was rejected. Workload identity audiences are chosen from the gateway's list. Requires migration `20261120001050`.
- Remove Redis. Runtime idempotency and per-recipient send limits for email, SMS and OTP, the gateway's refresh tokens and payment idempotency now live in PostgreSQL (migration `20261118000100`: `<runtime schema>.idempotency_keys` and `rate_limit_windows`, `apic_identity.refresh_tokens`, `apic_governance.payment_idempotency_keys`), purged by the retention job. Gateway rate limits, tribe quotas, traffic and usage dashboards count per instance in memory; dashboard metadata now reports `memory-window`. Readiness no longer reports Redis. Deployments drop every `*_REDIS_URL` setting.

### Fixed

- PayMongo payouts and wallet reads use the v2 endpoints. Linked merchant onboarding retains the original create reference when a write fails, and sandbox onboarding supports separate records per project.
- Members: a new member is invited and must sign in within 7 days. Before, the membership was active at once and never lapsed, so whoever first signed in with a mistyped or recycled address got access. An expired invite grants nothing until **Resend invite** renews it. Members can also be suspended and restored. Existing members are unaffected (migration `20261120001090`).
- Retention: usage records (90 days), quota counters (62 days) and key-issue receipts (30 days) are purged by the history purge job, which previously never touched the control-plane tables. A managed table that no longer exists no longer fails the job.
- Console: a failure that may clear by itself (the gateway busy or starting, a timeout, rate limiting, the network) is retried up to three times with backoff, honouring `Retry-After`; answers such as 403 or 404 are not retried. Error panels for those failures say so in plain words and offer Try again, which refetches every failed query on the page; the gateway's error code moves under Details. HTML error pages from a proxy no longer appear in messages.
- Console sign-in: the access check waits up to 15 seconds and asks once more before giving up, shows "Checking your access…" meanwhile, and on failure offers Try again without a new Google sign-in. A failed check answers 503 instead of 401, so open pages retry instead of saying you are signed out; an account without access answers 403.
- Console: an expired Google sign-in (about an hour) signs you out with "Your session ended" instead of failing every panel, and an expired stored sign-in is not reused after a reload. Signing out or signing in as someone else clears everything the previous person loaded.
- Console go-live: approving, rejecting or requesting activation shows the result at once, even if the refresh after it fails. Deciding a request someone already decided refreshes it instead of showing an error. "Request activation" appears only once existing requests have loaded, and when readiness cannot be checked the buttons say so instead of "Every readiness check must pass first".
- API access requests: an approval and a rejection made at the same moment can no longer both land, which could leave a rejected request with an active grant.
- People: changes to members, teams and project roles in one organization run one at a time, so two owners demoting each other at once can no longer leave the organization without an owner. Whether a change touches an owner is decided from the role at the moment of the change.
- Projects: a member who creates a project becomes its admin in the same transaction, so a failure can no longer leave a project its creator cannot see.
- Live activation: a request is accepted only when readiness passes and no request is open; a request is decided by ID, so older requests can still be decided; an approval expires after seven days; listing requests no longer recomputes readiness.
- Environments: an environment an APICenter operator suspended can only be resumed by an operator, and a suspended test environment issues no keys (migration `20261120001060`).
- Gateway: errors raised by the framework itself carry `UPPER_SNAKE_CASE` codes like every other error (`NOT_FOUND`, `VALIDATION_ERROR`, `RATE_LIMITED`, `METHOD_NOT_ALLOWED`) instead of reason phrases such as `"Not Found"` or the generic `HTTP_ERROR`. The unused `RATE_LIMIT_EXCEEDED` code is now `RATE_LIMITED`, as the runtimes already use.
- The idempotency guide no longer says the SDK never retries writes; it retries them with the same key.
- Gateway: a busy or unreachable database answers `503 DATABASE_BUSY` or `503 DATABASE_UNAVAILABLE` with `Retry-After`, instead of `500 INTERNAL_ERROR`. A duplicate record answers 409 and a vanished one 404. Console transactions wait up to 8 seconds for a connection instead of 2, so a briefly full pool queues requests instead of failing them.
- Gateway: console access checks are cached for 10 seconds per instance, and a project's organization until restart, so a console page checks roles once instead of once per request. Changes to members, teams and project roles drop the cache on the instance that made them; on other instances a removed role keeps working for at most 10 seconds.
- Gateway: the 24-hour usage summary is counted in the database instead of loading every request record.
- Gateway: live activation decisions and activation reject a malformed approval request ID with 400 instead of 500.
- Quota: every request counts under a usage key the gateway generates. Before, the caller's `X-Correlation-ID` was the key, so repeating one value made every request after the first free. An `Idempotency-Key` now makes retries count once only for `POST` to email, SMS, OTP and payments, whose runtimes replay the stored response, and only within one UTC day.
- Published APIs no longer receive the gateway's Cloud Run identity token. A tenant chooses the upstream, and a `*.run.app` upstream would have received a token APICenter's private runtimes accept.
- Workload bindings are listed and revoked only through their own project and environment. Before, a developer on one project could revoke another project's binding by ID.
- The gateway's audit log and HTTP metrics record the status the client received. Failed requests were recorded as 200, and a client that disconnects is now recorded as 499.
- Console: the dialog that shows a new key or signing secret once no longer closes on Escape; only "I stored it" closes it.
- Gateway (operations): one instance stays warm and each instance may open four database connections instead of two. Sign-in no longer times out on a cold gateway, and console pages no longer fail with `INTERNAL_ERROR` when the pool is exhausted.
- OTP: a code accepts five wrong attempts unless the project sets a different limit (1 to 10). Before, a project without OTP settings had no limit beyond the per-minute verify rate limit.
- SMS, OTP and email per-recipient rate limits use the normalised recipient and are kept per project and environment, so spacing or punctuation no longer resets a limit and one project cannot exhaust another's limit for a number.
- Payments: the gateway sends the signed runtime context, and the payments runtime scopes records by it once it has the context public keys, refusing requests without it in production. Before, the runtime token plus unsigned headers could name any project.
- Google sign-in runtime: production requires the signed runtime context instead of falling back to project headers.
- Organization-level audit events (members, teams, API access decisions) are stored. They were written with environment `unknown`, which the table's check refused, so they stayed in memory only; they now use `none`.
- Project-scoped console routes check that the project belongs to the organization in the path and answer 404 otherwise. Before, an organization owner or admin counted as admin of any project ID.
- Removing a member, a team member or a project admin assignment is refused with `409 LAST_PROJECT_ADMIN` when it would leave a project with no administrator and the organization has no owner or admin left.
- Suspending and resuming a test environment is audited as test; every event used to be recorded as live.
- Console toasts appear at the top center, so they no longer cover sheet and dialog footers.
- The console reads its deployment settings per request. Its pages were prerendered at build time, so a deployed console labelled itself `LOCAL` and decided whether to block `local-dev` sign-in from the build machine's environment. The deployment badge is gone; only local-development sign-in is flagged.
- Platform operators no longer type an organization ID: the sign-in membership lookup returns every active organization for them, and the console selects one and lists the rest in the organization switcher.
- The console treats Cloud Run as a deployment: `local-dev` sign-in is refused whenever `K_SERVICE` is set, instead of relying on `MANAGEMENT_PUBLIC_BASE_URL`. The Vercel and Render checks, the unused `@vercel/oidc` dependency and `.vercelignore` are removed; the console is deployed only to Cloud Run (`apicenter-management-test`).
- Published-API upstreams and webhook URLs can no longer reach internal addresses through IPv4-mapped IPv6. URL parsing and DNS write `::ffff:10.0.0.1` as `::ffff:a00:1`, which the private-address check in the gateway's upstream guard and the webhook delivery service treated as public, so an upstream such as `https://[::ffff:169.254.169.254]/` passed. Both checks now decode mapped, translated and IPv4-compatible forms and refuse anything that is not a valid public address.
- Test-environment access no longer reaches live resources. Changing a published API, rotating a webhook's signing secret and disabling an event destination now act only on the environment named in the path; before, anyone allowed to write to a project's test environment could change or disable its live APIs and webhooks and receive a new live signing secret. An API or destination outside that environment, including one in another project (previously a 400), is a 404.
- Adding a webhook endpoint works in deployed environments. Pub/Sub provisioning read `APICENTER_GCP_PROJECT_ID`, which no deployment sets, instead of `GCP_PROJECT_ID` like the rest of the gateway, so every new destination failed. Re-adding an endpoint for an application that had one before no longer fails: updating its existing subscription left out the filter, which Pub/Sub does not allow to change.
- Records created before the control plane (Serbizio's test payments and emails) now carry their organization, project and application directly. Migration `20261119000300` rewrites their legacy owner and service IDs using the control plane's migration mappings and removes the per-request owner mapping.
- Accept PayMongo webhooks on databases upgraded from the retired services. Their `shared_payment.payment_webhook_events` kept an old `environment NOT NULL` column and lacked the `(provider, provider_mode, provider_event_id)` unique index, so every webhook insert failed with a 502. Migration `20261119000100` aligns such databases with a fresh replay: it fixes that table, drops the retired services' leftover tables, views, columns, migration tracker and database roles, and removes `DELETE` from runtime roles. `db:verify:control-plane` now fails if any of it comes back or the webhook index is missing.
- Publish payment events as soon as a verified webhook queues them; the scheduled dispatcher job now only retries. Payment runtime errors without a status are logged with their path and trace instead of returning a bare 502, and failed webhooks log the provider event ID and type. The dispatcher job manifests use the deployed database secrets and no VPC egress.
- Live activation can be approved in the console: project admins see pending `environment.activate_live` requests with Approve and Reject. A decision requires a signed-in person and is recorded under their email; the requester still cannot approve their own request.
- Build shared contracts before compiling gateway images that consume project setup status types.
- Preserve gateway workspace-local dependencies through Docker build/runtime stages and keep the workspace directory layout for Node module resolution.
- Recognize completed PayMongo payments in active checkout sessions, refresh checkout reads by ID and reference, and reconcile saved status without regressing confirmed payments. Include webhook signing-secret references on gateway deployments.
- Refresh refunds from PayMongo on reads and apply signed refund status events without regressing terminal refund states.
- Reconcile payment-link archive responses against the current owner so concurrent paid webhooks and provider archive fields are both preserved.
- Persist fresh payment-intent, subscription, and invoice reads while preserving owner metadata and confirmed terminal states. Clear completed intent redirects and preserve aggregate versions when provider facts are unchanged.
- Register the provider payment found during checkout polling so the existing refund path can resolve it.

### Added

- Request diagnostics record the calling application for shared-service, payment and published-API calls (`caller` on the request), and the audit log names it.
- Signed HTTPS webhooks for payment events, usable by any backend: `POST …/event-destinations/webhooks` takes a public HTTPS URL and returns a `whsec_` signing secret once; `…/rotate-secret` issues a new one and keeps the old one signing for 24 hours. The new `apps/webhooks` delivery service receives each event from the destination's filtered Pub/Sub subscription, signs it in the Standard Webhooks format and POSTs it, refusing private and internal addresses at connect time; Pub/Sub retries anything not answered with 2xx and dead-letters it after the attempt limit. URLs and secrets live in Secret Manager (`apicenter-webhook-<id>`). SDK `verifyWebhook(rawBody, headers, secret)` verifies a delivery and returns the payment event. Requires migration `20261119000200`.
- Add the APICenter control plane: organization-owned projects with separate test and live environments, applications with explicit grants, and `ak_test_`/`ak_live_` application keys. Applications call every shared service and payments without registering a service, URL or routes; the gateway forwards a short-lived Ed25519-signed runtime context that every runtime verifies. Adds console roles (owner, admin, developer, viewer), teams and project roles enforced by the gateway; PostgreSQL row-level tenant isolation; project plans, request budgets and usage; approved live activation; optional published APIs with approved cross-project grants and SSRF-guarded upstreams; per-environment payment event destinations; and a fenced, shadowed, reversible migration from tribes, projects and services. Requires migrations `20261114000100`–`20261114000900` and runtime context keys.
- Add the console Workspace section (Projects, People, Migration).
- SDK 2.1.0: `auth: { apiKey }` for application keys, `createContextVerifier` for published APIs, and payment event contract 1.1 (`ownerGroupId`, `ownerProjectId`; `ownerTribeId` kept for 1.0 consumers).
- Contracts 0.2.0 for SDK 2.1.0: the published contracts package now carries the shared-service HTTP operations and payment event contract 1.1 (0.1.0 shipped with SDK 2.0.0).
- Add redacted request diagnostics and tenant-scoped payment event replay with immutable operation IDs and reconciliation gates.
