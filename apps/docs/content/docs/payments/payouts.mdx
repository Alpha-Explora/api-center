---
title: "Payouts"
description: "Pay the people who deliver your service out of the payments you collect: weekly, or when they cash out."
---

Payouts let your project pay the people who deliver your service, such as drivers, riders or service providers. This guide calls them **payees**.

1. You register each payee and set where they are paid: a GCash or bank account, through InstaPay.
2. When you take a payment, you say how much of it belongs to which payee. That share is an **allocation**.
3. APICenter holds each allocation once the payment is paid, until you **release** it. For example, release it when the job is finished.
4. After the settlement hold expires, released earnings are pooled per payee. They are paid in a **weekly payout**, or earlier when the payee **cashes out**. One transfer covers many jobs, so the transfer fee is paid once rather than once per job.

For a Node.js backend, use `api.payments.payees`, `api.payments.allocations` and `api.payments.payouts` from the [APICenter SDK](/guides/sdk-usage). The REST examples below are for other runtimes.

All amounts are in centavos.

## What is available now

Payouts are being rolled out in stages: new features open in test first, then in live. Build against the whole API now. Where a feature is not open yet, calls refuse with a stable error code instead of behaving differently later.

| Feature | Test | Live |
| :--- | :--- | :--- |
| Payees, destinations and verification records | Available | Available |
| Allocations: hold, release, cancel, refund recovery | Available | Available |
| Earnings (`GET /payees/{payeeId}`) and the payout list | Available | Available |
| Sending payouts: the weekly payout and cash-out | Available, simulated: transfers succeed at once and never reach the payment provider, whose test mode has no payout wallet | Not available yet. Cash-out returns `409 PAYOUTS_LIVE_DISABLED`. |
| [Payee wallet onboarding](#test-payee-wallet-onboarding) | Pilot, simulated identity check: turn it on for your project in the console | Not available yet |
| A merchant account of the project's own | Available: turn it on for your project in the console | Not available yet. Payments are collected through APICenter's account, and nothing changes in your integration when it opens. |

The console's **Payouts** page shows availability in each environment. When APICenter pauses sending, cash-out returns `409 PAYOUTS_PAUSED`. Earnings are kept for the next eligible payout after sending resumes.

## Settlement hold

A paid share becomes eligible seven days after payment by default. APICenter operators can set a project environment's hold to 0–30 days. Release the share using your own fulfillment rules. The hold uses the original payment confirmation time.

The earnings response reports released shares still inside the hold in `settling`. These shares become `available` when the hold expires. A cash-out with only settling earnings returns `409 IN_SETTLEMENT`.

## Register a payee

- **Endpoint**: `POST /api/v1/payments/payees`
- **Required scope**: `payments:payouts:write`
- **Required header**: `Idempotency-Key`

```bash
curl -X POST https://api.apicenter.itsandbox.site/api/v1/payments/payees \
  -H "Authorization: Bearer $APICENTER_API_KEY" \
  -H "Idempotency-Key: payee-provider-0042" \
  -H "Content-Type: application/json" \
  -d '{ "externalRef": "PROVIDER-0042", "legalName": "Juan Dela Cruz" }'
```

`externalRef` is your own identifier for the payee, and payout events carry it as `referenceId`. Registering the same `externalRef` again returns the existing payee with `200`.

`legalName` must match the name on the payee's account. A name mismatch is the most common reason a transfer fails.

## Set where the payee is paid

- **Endpoint**: `PUT /api/v1/payments/payees/{payeeId}/destination`
- **Required scope**: `payments:payouts:write`
- **Required header**: `Idempotency-Key`

```ts
await api.payments.payees.setDestination(payee.payeeId, {
  type: 'instapay',
  bic: 'GXCHPHM2XXX', // GCash
  accountNumber: '09171234567',
  accountName: 'Juan Dela Cruz',
}, { idempotencyKey: 'payee-0042-destination-1' });
```

A destination is one of two types:

- **`instapay`**: a GCash or bank account. It needs the receiving institution's code, `bic`; GCash's is `GXCHPHM2XXX`.
- **`wallet`**: a wallet at APICenter's payment provider. It needs no `bic`. (`provider_wallet` means the same and is deprecated: it is accepted until 2027-03-01, and responses that show it carry `Deprecation` and `Sunset` headers.)

Responses show the account number masked, as `accountNumberLast4`.

**24-hour hold.** After a destination changes, payouts to that payee wait 24 hours. The time the hold ends is in `destinationHoldUntil`. This protects payees if someone takes over their account and changes the destination. Sending the same destination again does not restart the hold.

Have the payee confirm a destination change in your app, for example with a one-time code from the [OTP service](/guides/messaging-verification/otp).

## Record how you verified a payee

Your project verifies its payees and records who performed the check, when it happened and what method they used. APICenter can require a verification record before a live payout.

Use `PUT /api/v1/payments/payees/{payeeId}/verification` with the `payments:payouts:write` scope and an `Idempotency-Key`.

```ts
await api.payments.payees.recordVerification(payee.payeeId, {
  verifiedBy: 'operator-17',
  verifiedAt: '2026-11-24T04:00:00Z',
  method: 'government_id',
  reference: 'verification-0042',
});
```

Use your own record identifier for the optional `reference` field. Keep identity document numbers and images in your own verification system. If verification is required, cash-out returns `409 PAYEE_NOT_VERIFIED` until you record the check.

## Test payee wallet onboarding

**Test only for now.** This is a pilot. Turn it on for your test project under **Payouts → Project payout access** in the console; while it is off, these calls return `503 PAYEE_ONBOARDING_DISABLED`. It is not available in live yet.

With the feature enabled for your test project, you can start wallet onboarding for an existing payee.
Use a test key with `payments:payouts:write` to start onboarding, reissue a verification link, and request activation.
Use `payments:payouts:read` to fetch the current status.

```ts
const onboarding = await apicenter.payments.payees.startOnboarding(payee.payeeId, {
  firstName: "Juan",
  lastName: "Dela Cruz",
  email: "juan@example.com",
});

if (!isPending(onboarding) && onboarding.verification) {
  // Present this URL only to the payee for whom it was issued.
  const { url, expiresAt } = onboarding.verification;
}
```

The API returns a new hosted link only on the response that issued it. Status reads and idempotent replays
return `verification: null`. To issue a new link, call `reissueOnboardingLink(payeeId)` with a new idempotency key.
In test the identity check is simulated, because the payment provider's test mode has none: it passes as soon as the link is issued, and the link is a placeholder.

Listen for `payee.onboarding.updated`, then read `getOnboarding(payeeId)`. When `nextAction` is `activate`,
call `activateOnboarding(payeeId)`. In test, activation attaches a simulated wallet in the payee's name as the payee's destination
and starts the 24-hour destination hold. Your application owns payee eligibility and release rules.
Provider wallet onboarding is test-only. The [project verification record](#record-how-you-verified-a-payee)
continues to govern payouts where the project requires it.

## Attach allocations to a payment

Add `allocations` when you create a checkout, a payment intent or a payment link. Your application key needs that resource's write scope.

```ts
await api.payments.intents.create({
  referenceId: 'BOOKING-1042',
  amount: { amountMinor: 50000, currency: 'PHP' },
  allocations: [{ payeeId: payee.payeeId, amount: { amountMinor: 42500, currency: 'PHP' } }],
}, { idempotencyKey: 'booking-1042-attempt-1' });
```

The allocations may not add up to more than the payment; the difference is your platform's share. Each payee may appear once per payment, and one share is at most ₱50,000 (the most one InstaPay transfer can carry). Retrying the create with the same `Idempotency-Key` stores each share once.

Validation runs before the payment is created:
- **`404 PAYEE_NOT_FOUND`**: a payee doesn't exist, or belongs to another project.
- **`409 PAYEE_SUSPENDED`**: a payee is suspended.
- **`400 ALLOCATIONS_EXCEED_AMOUNT`**: the allocations add up to more than the payment.

An allocation's status moves like this:
- It is `awaiting_payment` until the payment is paid.
- It is then `held`, and you receive the [`payment.allocation.held`](/guides/events/webhooks) event.
- A payment link can be paid many times. Each paid payment gets its own copy of the link's allocations.

## Release or cancel an allocation

- **Endpoints**: `POST /api/v1/payments/allocations/{allocationId}/release` and `POST /api/v1/payments/allocations/{allocationId}/cancel`
- **Required scope**: `payments:payouts:write`
- **Required header**: `Idempotency-Key`

**Release** a held allocation when your own completion rule is met, for example when the job is done. Released earnings are paid in the payee's next payout.

**Cancel** an allocation that should never be paid out, for example when the work was not done.

An allocation that is already pooled or paid can't be cancelled; you get `409 INVALID_ALLOCATION_STATE`. Refund the payment instead.

## When payees are paid

**Test only for now.** Sending payouts works in test and is not available in live yet; see [What is available now](#what-is-available-now).

| Payout | When | Who pays the transfer fee |
| :--- | :--- | :--- |
| Weekly | Every Friday at 8:00 PM Philippine time | Your platform |
| Cash-out | When you call `POST /api/v1/payments/payees/{payeeId}/cash-out` | The payee |

**Cash-out limits.**
- A cash-out needs at least ₱100 released.
- A payee can cash out at most ₱10,000 a day.
- Whole allocations are paid, oldest first, up to that limit.
- A refusal is `409`, with one of these codes:
  - `BELOW_CASH_OUT_MINIMUM`
  - `DAILY_CAP_REACHED`
  - `DESTINATION_HOLD`
  - `NO_DESTINATION`
  - `NOTHING_RELEASED`

**Your settings.** Your project's settings can change any of these: the weekly day and time, the cash-out limits, and who pays the fee. Ask your APICenter administrator.

**Fees.** Each transfer costs about ₱10. When the payee pays the fee, it is deducted from the payout's `net`.

**Large balances.** A single transfer is limited to ₱50,000. A larger balance is paid across several payouts; a share that does not fit in this payout waits for the next one.

## Follow a payout

- **Endpoints**: `GET /api/v1/payments/payouts`, `GET /api/v1/payments/payouts/{payoutId}` and `GET /api/v1/payments/payees/{payeeId}`
- **Required scope**: `payments:payouts:read`

`GET /payees/{payeeId}` includes the payee's `earnings`:

| Field | Meaning |
| :--- | :--- |
| `awaitingPayment` | Allocations whose payments are not paid yet |
| `held` | Held until you release them |
| `available` | Released and not yet paid, after any refund clawbacks |
| `inFlight` | Payouts that have been sent but are not yet confirmed |
| `paidThisWeek` | Paid since Monday |

A payout ends as `paid` or `failed`, and each sends an event:

- **`payment.payout.paid`**: the money reached the payee.
- **`payment.payout.failed`**: the transfer did not go through. The earnings go back to the payee's balance and are paid in a later payout. Check the payee's destination; `failureCode` says why.

**`unknown` and `needs_review`.** While a payout is `unknown`, APICenter is confirming the transfer with the provider. A payout that needs a person to check it is `needs_review`. In both cases the payout is never sent twice.

## Refunds

| When the refund happens | What happens to the payee's share |
| :--- | :--- |
| A full refund, before the allocation has been paid out | The allocation is cancelled |
| A partial refund, or a refund after the payout | The payee's proportional share is recovered from their next payout |

## Events

| Event | `referenceId` | `data` |
| :--- | :--- | :--- |
| `payment.allocation.held` | The payment's reference | `allocationId`, `payeeId`, `paymentId`, `amount`, `currency` |
| `payment.payout.paid` | The payee's `externalRef` | `payoutId`, `payeeId`, `net`, `fee`, `currency`, `trigger` |
| `payment.payout.failed` | The payee's `externalRef` | `payoutId`, `payeeId`, `net`, `fee`, `currency`, `trigger`, `failureCode` |
| `payee.onboarding.updated` | The payee's `externalRef` | `onboardingId`, `payeeId`, `status`, `attempts` |

Events go to the application that created the payee, or the payment for `payment.allocation.held`. See [webhooks](/guides/events/webhooks) for delivery and verification.
