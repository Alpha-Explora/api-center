Use this checklist when a backend starts using APICenter. The [Management guides](/guides/management/access-and-tenancy) explain organizations, projects and applications; the [SDK guide](/guides/sdk-usage) covers installation and API methods.

## Before integration

- Create an application for the backend in the right organization and project, and grant it only the actions it needs.
- Issue an `ak_test_` key for the test environment, and an `ak_live_` key once the live environment is approved.
- Store the key as `APICENTER_API_KEY` in the backend secret manager. Never send it to a browser or commit it.
- Add the package's GitHub Packages configuration and a CI token with package read access.
- If payment lifecycle events are part of the integration, add a [webhook destination](/guides/events/webhooks) for the backend's HTTPS endpoint in each environment and store its signing secret.
- Make event processing idempotent by `eventId` and monotonic by `aggregateVersion`.

## Create a payment checkout

Create a stable idempotency key for the business operation and persist it with the order before calling APICenter. Reuse it after timeouts or transient failures.

```ts
const checkout = await api.payments.checkouts.create(
  {
    referenceId: order.id,
    amount: { amountMinor: order.totalMinor, currency: 'PHP' },
    successUrl: 'https://orders.example/payments/success',
    cancelUrl: 'https://orders.example/payments/cancel',
  },
  { idempotencyKey: order.checkoutRequestKey },
);
```

Treat the checkout as pending until your service processes the `payment.checkout.paid` event. A browser redirect alone does not prove payment. Payment resource IDs are opaque APICenter IDs; do not depend on provider-specific fields.

## Process payment events

Verify each delivery's signature with the endpoint's signing secret (`verifyWebhook` in the SDK). Ignore an `eventId` already recorded, and apply only an event whose `aggregateVersion` is newer than the version stored for that resource. Answer 2xx for a valid duplicate after confirming it was already applied. See [payment event webhooks](/guides/events/webhooks).

## Handle failures and rollbacks

Retry a transient API failure with the same idempotency key and body. Do not issue a new key just because the first response timed out; the original operation may have completed.

For an event delivery failure, ask the APICenter operator to inspect the webhook destination's deliveries. After correcting the consumer, replay the event and retain its original `eventId` and aggregate version. If a payment cutover rollback is announced, continue serving the consumer's existing local state and pause new payment commands until the operator confirms the path forward. Do not call the payment provider directly.

When escalating, include the environment, APICenter resource reference, event ID, and correlation ID. Never include API keys, webhook signing secrets, or provider credentials. Operator procedures remain in the internal `docs/` collection.
