---
title: "Authentication and grants"
description: "Application keys, environments, and the grants that decide what an application may call."
---

APICenter authenticates your backend with an **application key** and authorizes each call against the application's **grants**.

## Application keys

A key belongs to one application in one environment of one project. Its prefix names the environment: `ak_test_…` or `ak_live_…`. Send it as a bearer token; the SDK does this from `APICENTER_API_KEY`:

```ts
import { ApiCenter } from '@alpha-explora/apicenter-sdk';

const api = new ApiCenter();
```

For a call without the SDK, send `Authorization: Bearer ak_test_…` to `https://api.apicenter.itsandbox.site/api/v1/...`, and an `Idempotency-Key` header on every write.

Keys are shown once when issued, can carry an expiry, and can be revoked at any time; a revoked key fails with `CREDENTIAL_REVOKED`. Keep keys in a server-side secret store, one per application and environment. Never put one in browser or mobile code.

## Grants

Nothing is allowed by default. An application may call an action only when its environment has the capability enabled and the application holds a grant for the action:

| Capability | Example actions |
| :--- | :--- |
| Email | `email:send`, `email:read` |
| SMS | `sms:send`, `sms:read` |
| OTP | `otp:generate`, `otp:verify`, `otp:read` |
| Geo | `geo:geocode`, `geo:reverse-geocode`, `geo:geofence` |
| Google sign-in | `gauth:authorize`, `gauth:token`, `gauth:logout` |
| Payments | `payments:checkout:write`, `payments:checkout:read`, `payments:refunds:write`, `payments:payouts:read`, `payments:payouts:write`, … |

A call without the grant fails with `ACTION_NOT_GRANTED` (a `PermissionError` in the SDK); a disabled capability fails with `CAPABILITY_NOT_ENABLED`. `await api.whoami()` lists the key's grants.

Live environments are activated after an approval by a person other than the one who requested it, and their keys are issued separately from test.

## Human access to the console

Console sign-in is separate from application keys. A person signs in with an authorized Google account and needs a role in the organization or project (owner, admin, developer or viewer). Ask an organization administrator to add you. See [Access and tenancy](/guides/management/access-and-tenancy).
